# Cairn v0.11.1

`v0.11.1` (`drystane-cairn==0.11.1`) follows v0.11.0. It fixes two faults in
the graph projection: bulk loading at a large `delivery.chunk_size` could
exhaust the memory of FalkorDB and of Cairn, and a memory with a backdated
`valid_from` could end a newer fact in the graph. It also records the rule
that graph end dates never hide a memory. The REST contract, catalogue schema,
Attic format, client commands and locked dependencies are unchanged, and no
rebuild is required. This release ships source and local build recipes, not
container images: `CAIRN_IMAGE` and `CAIRN_EDGE_IMAGE` in `deploy/images.lock`
name local source-build tags. Garden remains Linux only.

## Fix: bulk loading could exhaust memory at a large chunk size

With `delivery.chunk_size` above 1, Cairn projects memories into the graph in
chunks. Graphiti saves a chunk's episodes and edges with one query per kind,
and the FalkorDB client writes query parameters into the query text, so each
edge travelled with its 1,024-number embedding as text. A chunk of 500
memories at the extraction density of v0.11.0 (about 31 graph edges per
memory) became a single query of about 190 MB. FalkorDB needed about 700 MiB
beyond its final size to accept it, and building the text cost the Cairn
process about 630 MiB. Under a 1 GiB memory limit either process could be
killed. When FalkorDB was the one killed, Cairn logged
`projection_bulk_demoted` and fell back to projecting one memory at a time,
which is correct but many times slower.

Cairn now sends such a write as consecutive queries of at most 200 rows. The
result in the graph is the same. Measured without a model provider, on
synthetic extraction at that density and one run per number:

| One chunk of 500 memories, empty graph | v0.11.0 | v0.11.1 |
|---|---|---|
| FalkorDB peak | about 980 MiB | about 340 MiB |
| Cairn process peak | 1,649 MiB | 1,021 MiB |

What remains in the Cairn process is not a leak and does not grow from chunk
to chunk: Graphiti holds every edge and entity of a chunk, with its
embedding, until the bulk call returns, so the peak scales with the chunk
size. Three consecutive chunks of 200 peaked at about 540 MiB each.

**Recommended setting.** `delivery.chunk_size` keeps its maximum of 500, so
existing configurations load unchanged, but 200 is now the recommended value
for bulk loading and rebuilds (ruled 23 November 2026). Throughput gains
little beyond 100. As a guide at the density above, allow the Cairn process
about 370 MiB over its resting size at 200 and about 860 MiB at 500, and size
FalkorDB for its graph with some headroom for search during a chunk. The
default of 1 is unaffected.

Not measured: a chunk of 500 against an already large graph, and real
extraction, whose edge count per memory varies with the text.

## Fix: a backdated memory could end a newer fact in the graph

When two facts in the graph contradict each other, Graphiti ends whichever
has the earlier date. Cairn gave the graph only the time a memory was
recorded and ignored `valid_from`, so an older statement recorded later, for
example by an import or a late save, ended the newer and still true fact.

The graph is now given a memory's `valid_from` when it is earlier than the
time of recording. A `valid_from` later than the recording time is not used:
the text was written when it was recorded, and relative dates in it are
resolved against that moment.

For such backdated memories the reference time is now part of the extraction
cache key, because cached extraction carries dates resolved against it. The
key of every other memory, and every existing cache row, is unchanged.

Existing graphs keep their dates until a memory is projected again. Nothing
visible depends on that, for the reason in the next section; the next
`cairn rebuild-index`, whenever one is run, picks the dates up and extracts
backdated memories afresh.

## Rule: graph end dates never hide a memory

A decision of 23 November 2026 is now part of the project's recorded
decisions: the end dates Graphiti puts on a graph fact are advisory. Recall searches every matching graph fact,
ended or not, and takes its source memories as candidates. What hides a
superseded memory is the catalogue: invalidation, correction and resolution.
This describes what recall already did; a test now holds it.

## Known and not changed

- Contradiction judging in the graph occasionally ends a fact that a later
  memory does not contradict. A replay of 472 recorded judgements, three
  passes, found Cairn's batched prompt wrong on zero or one of about 4,700
  fact pairs per pass, and judging one fact per call wrong more often, so
  batching is not the cause. By the rule above this does not change what
  recall returns.
- When the graph database goes away during a bulk chunk, the
  `projection_bulk_demoted` log entry does not say so; it carries the same
  code as other adapter failures.
- In the first seconds after a start, recall has been seen to answer in its
  lexical mode with `semantic_degraded: true` and to return to normal
  without intervention. The cause is not yet established.

All three are open issues.
